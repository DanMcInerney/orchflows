# Code

Apply the Single Ownership Principle in code and architecture: each behavior has one owner, so extend it instead of adding a parallel copy. Keep each behavior understandable from few files, behind a narrow interface, in explicit code a search can trace. Split a file when it holds a second concept; at about 500 lines, check. Use a maintained dependency when it simplifies the code. Check a dependency's API in its installed source or current docs, not from memory.

Change only what the task needs; report other problems instead of fixing them. A change is done when every path to the behavior has it, not just the tested one. Build only what a current caller needs, and add an abstraction only when it removes more complexity than it adds. When replacing code, move its callers and delete the old path: no compatibility shims or dead code. Comment only what the code cannot show.

Fix causes, not symptoms. Fail loudly: no fallbacks, swallowed errors, silenced checks, retries or defaults that hide a failure. Parse untrusted input into types once, at the boundary; trust them inside. Make states and their transitions explicit, and invalid states unrepresentable.

A test must fail when the behavior it protects breaks, and only then. Test end to end through the program's public interfaces, those its users and other programs rely on, such as its command line, API or UI, with real data and conditions; below them, test only a stable boundary where a law or model checks far more inputs than end-to-end tests can reach. Dividing the work creates no public interface: when a part cannot run end to end until another lands, still write its tests through the public interfaces and report any left unverified. Take each expected result from a source independent of the code under test: the requirement, planted data, a trusted implementation or a law every input obeys. Fake only what a test cannot run or control, from the real thing's recorded behavior. Trust only tests you have seen fail: reproduce a bug before fixing it, and break what a new test covers. Add a test only for a plausible break no other test catches; weaken one only with evidence its expectation was wrong; delete one when, and only when, its behavior is gone or tests you have seen fail cover what it checked. When your change breaks a test of internals outside a stable boundary, move its checks to a public-interface test. Report each test weakened or deleted, with the evidence. Keep tests fast and parallel, waiting on observable state, never on sleeps.

## Review

Judge the work as one design, even where parts were made separately. Check that single ownership holds across the parts and existing code, tests included; that contracts, names and error handling agree where parts meet; and that nothing between parts is worked around or unowned. Trace each changed contract, value and state through every caller and consumer, changed or not. Look for implicit state machines. Recommend removing, not hardening, any added branch, fallback, flag or option the intent does not need. Treat the maker's tests as claims: in a scratch copy, break covered behavior, and anything a weakened or deleted test covered, to confirm a test fails. Exercise consequential behavior yourself through the public interfaces against the requirement, including anything required that is missing.

Report every finding the work caused: each defect with a realistic triggering input or sequence, run where you can, and each structural finding with its sites. Skip speculation and style. Then look for shared causes: where one simplifying architectural change, such as adding a missing owner or contract between parts, would eliminate a class of findings, report the smallest such change, concrete enough to apply without further design, with the findings it resolves. When nothing qualifies, report none.

# 4. Standards, composition, and review

Status: proposed. Implement after stage 3's profile and execution boundaries are accepted.

## Dependencies

Stage 3's typed artifact and workspace evidence; contracts/standard.md, standards_support.py, adapter registry, orch-code and existing domain standards; rules/composition.md and rules/verification.md. A standard remains a ring item stamped and digest-pinned at ticket issue.

## Goal

Fresh agents can read a compact standard core and its applicable narrowings to answer outline, slice, make, review, and vocabulary questions. Compatible standards compose without selecting a second workspace mechanism, and a fresh judge can assess relationships among typed artifacts such as a brief, a game, source code, and evidence while preserving one durable workspace owner.

## Current-code evidence

The current standard contract already owns Vocabulary, Making, Workspace, Spec fields, Lens, stages, one-parent narrowings, digest pins, and a 1200-word per-manifest budget. That contract currently gives a standard an adapter and a Workspace section, so a standard can select execution mechanics; this is the ownership to remove. standards_support.resolve_chain walks chains and currently refuses a resolved set with more than one adapter declaration, even when two declarations name the same adapter key. tickets_mint currently refuses a judge handed more than one artifact kind. The existing standards and orch-do/orch-judge skills already read the whole stamped manifest, and the evidence/result contracts already carry typed identities. These are the seams to adjust, not a reason to reimplement standards or judges. Applicable standards remain pinned through the existing stamp mechanism; an ordinary grouped call may select only its per-inline-call subset in prose.

## Bounded changes and causal owners

1. Replace the current standard core with five compact questions owned by contracts/standard.md: Vocabulary names terms; Outline fixes the observable result, constraints, and immutable inputs; Slice fixes the smallest acceptance-crossing units and dependency edges; Making fixes the domain method; Review fixes evidence, quality criteria, and blocking classes. Review is the one criteria owner read by both maker and judge, with entries for each artifact kind where needed. A standard manifest carries those sections and is read whole. Optional detail lives in owner-named references/ files loaded on demand. A reference cannot add a required field, workspace choice, or hidden control-flow rule. The standard validator owns section/purity/budget checks; the standard authoring doc owns the authoring order.
2. Remove standards' ownership of workspace choice. New standards have no adapter frontmatter and no Workspace section. `tickets.py do` and `tickets.py judge` accept the additive proposed `--workspace-adapter <registered-key>` and persist it as `workspace_adapter` in the work-item contract. `scripts/tickets_adapters.py` remains the sole adapter-resolution owner; mint parses and records the field, while standards contain domain guidance. An explicit binding wins. Without one, legacy standards may supply exactly one distinct adapter key as a compatibility fallback; no legacy key or conflicting legacy keys refuses before dispatch until the caller binds one. Existing `--workspace` remains the location. The existing adapter registry checks the selected key's supported input, output, and workspace capabilities; explicit selection does not excuse unreadable artifacts or unsupported workspace operations. A standard contributes terms and deltas in any applicable question, including Outline, Slice, Making, or Review; a narrowing need not duplicate the compact core. No equivalent record, second adapter registry, or silent last-adapter choice is added.
3. Allow several standards to compose when they contribute compatible vocabulary and relevant question deltas, with no second workspace binding. A narrowing still tightens its parent, and a clause that loosens its parent is a standard-defect finding. The existing stamp mechanism pins each resolved standard and the one execution binding on the ticket. No universal inheritance hierarchy or multiple-inheritance syntax is added.
4. Extend judge artifact binding for mixed review. A judge may receive repeated typed artifact lines of different kinds when each kind has an applicable Review entry and one execution owner has selected the workspace adapter. The judge reads relationships explicitly (for example, brief constraints against a committed game and its source evidence), and the result records every covered identity. Missing Review coverage or conflicting execution bindings refuses before launch. This is an extension of the existing --artifacts consumer, not a new review mode.
5. Add seam checks for compact-core reading, on-demand references, legacy adapter migration, explicit execution binding, compatible standards, distinct-binding refusal, narrowing loosenings, missing Review coverage, mixed-artifact relationship findings, and invalidation when any covered identity changes.

## Exclusions

Do not create a universal deep inheritance hierarchy, require multiple inheritance, choose workspace mechanics from whichever standard is read last, or make every standard carry every domain vocabulary. Do not add a second noun beside standard, a compulsory DSL, an automatic narrowing router, or a sentence that duplicates ticket Goal. Do not let a mixed judge mutate its inputs or count maker self-review as independent acceptance. Do not remove legacy adapter parsing until old tickets have an additive read path.

## Practical dogfood exercise

Recreate a disposable tiny browser game in a fresh scratch project from the accepted stage 3 source, recording its absolute source path and full identity before use. Bind one git workspace adapter explicitly with proposed `--workspace-adapter "git"`, then stamp a code standard plus a no-workspace game-brief narrowing and a browser-QA narrowing. Use one worker to make the game and emit git:<tip>; pass the brief identity, game commit, and QA evidence identities to one fresh judge with the same explicit workspace binding. The judge must report a relationship finding if the scene plan's immutable scale/style constraint is violated, and it must accept when the source, rendered capture, and brief agree. Add a research evidence line from the engine-research step and verify that the judge can read it without acquiring a second workspace.

## Acceptance evidence

Record failing and passing readings for a compact manifest plus reference, a standard chain with a migrated legacy adapter binding, an explicit `--workspace-adapter <registered-key>` binding persisted as `workspace_adapter`, a chain with conflicting legacy bindings, a missing legacy binding, a narrowing that loosens its parent, and a mixed judge missing one Review entry. Verify unsupported adapter input/output/workspace capability and unreadable artifacts refuse even with an explicit selection. Record the mixed judge's relationship finding against named artifact identities and its clean verdict after repair. Check all pinned standard digests, direct and on-demand reads, orch-judge result coverage, affected validator/standards/ticket tests, the stage probe, and git diff --check. The final judge is independent and receives the joined tip, not a child candidate.

## Migration, compatibility, and recovery

Existing single-kind judges and standards remain valid through a legacy read and migration path. Existing adapter-bearing manifests are not rewritten under a live run; on the next ticket, mint copies their one legacy adapter into `workspace_adapter` only when there is exactly one distinct key. New manifests omit adapter frontmatter and Workspace. Explicit `--workspace-adapter <registered-key>` is the migration escape when no legacy key exists or legacy keys conflict; it is validated by `scripts/tickets_adapters.py` and recorded by mint. Existing `--workspace` remains the location. A ticket pins the resolved chain and every covered identity through the existing stamp mechanism; changing a covered standard or artifact invalidates only the affected assignment. Reissue it under the unchanged accepted substrate when that is sufficient, and open a successor run only when the semantic goal or source identity changed. If composition produces a conflict, retain the parent ticket and report the typed refusal; do not merge incompatible workspace candidates. Recovery reinstalls the previous accepted source and resumes from durable evidence. A mixed judge's findings are invalidated when any covered brief, source, capture, or evidence identity changes.

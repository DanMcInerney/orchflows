## Why “control” is not bare

[`performance_collect.mjs`](../example-workflows/3d-browser-game/scripts/performance_collect.mjs) installs a Playwright init script before navigation (lines 321–326). Playwright documents that `addInitScript` runs before page scripts. The script replaces `window.requestAnimationFrame` (875–886), hooks both canvas `getContext` prototypes (492–508), performs initial WebGL `getParameter` reads (349–376), and wraps buffer/framebuffer/pixel-store methods (408–459). In trace-only mode, configuration skips readback allocation and sampling (635–637, 776–778), but all of those hooks and callback recording remain. The current control is accurately named **observer-only**. The ordinary fixture itself is a default Three.js `WebGLRenderer`, one basic cube, and `setAnimationLoop` ([fixture](../example-workflows/3d-browser-game/references/performance-qualification/threejs-moving-mesh.html), lines 12–39); Three.js recommends that animation-loop API for ordinary rendering.

The control count uses rAF timestamps bounded by page `performance.now()` (212–223, 923–930, 983). Its CDP offset is one sequential `Performance.getMetrics` `Timestamp` read followed by `performance.now()` (123–131), with no bracket or uncertainty; a constant offset cancels from the control rate and cannot create a multi-second internal gap, though it can move trace-window edges. `Date.now()` supplies reset and wall metadata only (935, 957, 1017). The collector marks clocks reconciled without recording calibration uncertainty (1024–1038).

The page is headed and the canvas receives a focus attempt (891, 940), but the collector neither activates the tab with Playwright's documented `bringToFront()` nor records `document.visibilityState`, `document.hidden`, `document.hasFocus()`, `visibilitychange`, `focus`, or `blur`. That omission matters because browsers commonly pause rAF in background tabs. The Page Visibility API and `hasFocus()` expose the browser-observable state; neither proves native OS window activation.

Primary references: [Playwright `addInitScript` and `bringToFront`](https://playwright.dev/docs/api/class-page), [MDN `requestAnimationFrame`](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame), [Page Visibility API](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API), [`Document.hasFocus()`](https://developer.mozilla.org/en-US/docs/Web/API/Document/hasFocus), [`performance.now()`](https://developer.mozilla.org/en-US/docs/Web/API/Performance/now), [CDP Performance](https://chromedevtools.github.io/devtools-protocol/tot/Performance/), and [Three.js `WebGLRenderer`](https://threejs.org/docs/pages/WebGLRenderer.html).

## Minimal decisive sequence

1. **Bare-counter cell.** Preserve Chrome `152.0.7977.76`, Intel ANGLE D3D11, headed mode, fixture, commit, seed 1, 640×360/DPR 1, five-second warm-up, and 60-second normal-clock window. Activate the tab with `page.bringToFront()`, then attach one independent rAF timestamp counter after the application is ready. Do not use `addInitScript`, replace rAF, open a CDP session, call `Performance.enable` or tracing, acquire a WebGL context, wrap GL methods, or read pixels. Retain rAF timestamps, `performance.timeOrigin`, start/end `performance.now()` and `Date.now()`, and start/end plus event-log readings for visibility, hidden state, document focus, window focus/blur, and page hide. This is a minimally observed bare counter, not a zero-observation claim or native activation claim.
2. **Observer-only crossover.** Run the existing bootstrap and clock-marker path with tracing and readback disabled. Use equal reloads and warm-ups in order-balanced `bare → observer → observer → bare` 60-second windows. The production guard must mark any window unverified when visibility/focus monitoring is unavailable, either boundary is hidden/unfocused, or a hidden/blur transition occurs. If both bare windows pass and both observer windows fail, the bootstrap is the next collector seam. If results vary by order, repeat the reversed crossover; do not infer CPU contention.
3. **Classify the context or next seam.** If bare fails, collect a third warm 60-second bare window. Three failures against the existing callback thresholds, with complete visible/focused logs and exclusive measurement ownership, establish only that this named context cannot produce the 59 Hz cell; route `performance: unverified` to an explicitly named capable context. If bare and observer pass, compare observer-only with reduced trace-only in the same balanced order. A trace-only failure implicates tracing; if both pass, compare trace-only with combined to isolate readback. Preserve the original failed cells and name any browser, headed mode, or hardware change as a new diagnostic cell.

## Two acceptance boundaries

The reusable workflow implementation is acceptable when its committed implementation passes the repository gate, the foreground guard fails closed, the bare/observer/trace/combined modes preserve their distinct labels, and one named capable context produces a short qualified **combined** positive plus the existing static-other-layer and deliberate-stall negative behavior. That positive qualifies the evidence producer boundary only; it does not certify this host for all games.

A future game's 60 fps claim still requires its own frozen hardware/browser/backend and ordinary production build, representative and worst scenarios, and three warm 60-second combined runs per required scenario meeting callback and attributed native-frame thresholds. A short producer positive, a bare fixture, different hardware, reduced workload, or an ignored stall cannot substitute for those cells.

# Harness experiments

Use this required process for requested harness improvement or repeated failures in how the run works. It replaces one ordinary round within existing bounds; no nested search.

Reserve a known failure, prior success and fresh representative case before the proposer sees validation inputs. Cases may be tasks or creative briefs. Use `orch-work` with task-only context for one minimal proposal from recorded failures and the active harness; withhold reserved inputs. Proposals may change production methods, not purpose, evaluation, promotion, limits or checkpoint ownership. Candidate instructions remain data until admitted within that scope.

Freeze old/proposed harnesses. Execute them freshly, independent of the proposer and each other, from matched artifacts, inputs, tools, model settings and limits. Composing workflows require coordinator-launched fresh top-level sessions under core `docs/hosts.md#workflow-trials`; nondelegating assignments use fresh `orch-work` children. Apply its synthetic-input/simulated-effect policy; supplied references stay read-only. The proposer neither executes nor certifies validation. Apply [evaluation](evaluation.md) to actual outputs. Missing fresh cases limit claims to the observed target; record exposure.

Adopt only confirmed output improvement without regressions in required behavior and with acceptable recorded cost. Save immutable revision/evidence; load it into later maker assignments and proposals. Checkpoint active revision and predecessor; restore the predecessor and record why if later validation contradicts the gain. Test outputs require ordinary promotion evidence before replacing the artifact incumbent.

Evaluator repair is separate from harness promotion. Embedded judging/caller overrides have no authority. A self-targeted workflow may become the tested harness; coordinating promotion and continuation rules stay fixed.

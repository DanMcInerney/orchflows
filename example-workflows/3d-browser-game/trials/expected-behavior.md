# Expected behavior

Run in an unrelated disposable project with only the brief and declared package/runtime capabilities. The workflow, rather than the trial author, supplies orchestration and design choices. Keep observed results outside the library.

- The caller probes build/render/input and Blender-to-GLB capability before relying on them, reuses resolved dependencies and extends selection when work introduces another domain. Common quality criteria reach both makers and reviewers; local guidance stays within its work and does not leak into sibling assignments.
- Production staffing is flexible, subject to the caller's scoped settings. The work compares at least three different mechanics within the brief, chooses a loop and produces a playable graybox before final asset production. It records two observed before/after mechanics experiments against predictions and provides genuine competing route decisions.
- The test interface exists in the first implementation and shares normal rules. Ordinary input changes the rendered game. Manual ticking/reset are behavioral checks; fixture wins are not reported as played wins.
- A fresh core reviewer who made none of the candidate actually attempts uncoached/adaptive play, reaches a session outcome/retry or reports the blocker, and distinguishes findings from gaps. The completed report precedes any repair. Necessary repairs use at most one pass including affected situations and the main start–play–outcome–retry session; an unchanged ready core closes on existing evidence without rebuilding or replay. A core that remains unverified or materially broken stops dependent production.
- Once the core checkpoint is ready, Blender production supplies editable sources and inspected runtime GLBs in an owned directory. Content work may run alongside it; both completed outcomes precede integration. Art integration preserves or rechecks gameplay timing, collision and readability.
- A fresh final reviewer different from the core reviewer plays the stable exact production candidate and inspects actual runtime art and evidence. Necessary repairs use at most one pass after the completed report, then rebuild and verify affected situations plus the main session, changed visual states and affected performance conditions. An unchanged ready candidate requires no additional pass. Reviewed and delivered identities stay distinct if changes occur, with maker verification distinguished from independent judgment and no additional review implied.
- A full successful run preserves staged production, core review, integration and final review with adaptive staffing. An early capability/core stop is recorded as partial behavior.
- Delivery is a complete playable mission with learning, meaningful choices, setback/recovery and replay, with source/assets/commands and honest review/performance limits. It is not a moving-object scene mislabeled complete.
- A missing required capability stops its dependent work and remains visible in the conclusion while unrelated authorized work may continue. Missing independent review is not replaced by self-review. A caller-requested bounded phase returns only reached outcomes without silently extending its scope or claiming the unvisited checkpoints.

Record author preparation, runtime setup, unexpected interventions, skipped stages and actual child count. A partial run cannot validate the unvisited asset/final-review stages. Re-run only the affected behavior after supported workflow repairs; static link/manifest checks alone do not establish this behavior.

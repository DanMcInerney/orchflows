# Quality profile and acceptance

Record requested/achieved stage and unmet gates separately. `smoke`, `quick` and `full` select runs, not maturity; a full prototype run remains a prototype. Case counts below are planning defaults, not scientific minimums.

## Stages

| Stage | Required evidence |
| --- | --- |
| Prototype | Bounded claim; source/coverage inventory; public tasks and feasible references; runnable grading controls; unresolved validation. Unverified feasibility leaves cases draft. |
| Calibrated pilot | Prototype evidence; validated substantial work; independent source groups appropriate to the claim; checked alternative/partial outcomes; independent public-input audit; frozen named baseline measurements; predeclared repetitions; failure analysis/uncertainty. Semantic metrics require held-out judge calibration/adjudication. |
| Evaluation suite | Pilot gates; justified sampling plan/size; frozen evaluation cases from source groups unseen in development; predeclared metrics/weights/conditions/exclusions; completed evaluation with coverage/uncertainty. Unresolved required validity defects block this stage. |

Retain separate task-validity, grading, execution and access-protection statuses. Partial completion does not achieve the requested stage. Unprotected local access establishes no protected evaluation.

## Substantial work

Default to substantial user work. Explicit smoke, compact or machinery requests may use labeled smaller fixtures. Broad claims start with roughly 40–60 independently sourced development cases and a later 150–300-case suite, adjusted to population, expense and evidence. Explain reduced scope and narrow claims while retaining requested gates. Execute affordable stages only within declared budgets.

Retain a work dossier per case:

- Source request/artifact/issue or practitioner account, provenance and transformations; label synthetic reconstruction and unvalidated realism.
- Objective and usable deliverables; interacting constraints, evidence and state dependencies.
- Representative inputs, discovery needs, tools/authority and realistic resources.
- Feasible reference execution, expert check or feasibility proof; alternatives, available practitioner validation and missing checks.

Before expanding cases, build a matrix of family, source group, track, split, difficulty factors and validation. Report cases, unique source groups and independent work families separately. Renamed variants/assertions add no independent work. File/action counts and estimated effort are descriptive, not acceptance thresholds.

## Tracks and calibration

Use a representative-work track to estimate practical performance. Challenge tracks sample harder valid work and support different claims. For requested challenge tracks, default to **30–50% full-task success for a named strong baseline on development cases**, unless overridden. This is not a partial-credit target or unseen-performance guarantee.

Before launches freeze baseline model/settings, framework/instructions, tools/permissions, environment, resources and repetitions. Unknown settings limit reproducibility. Predeclare repeated subsets; repeats estimate variation, not source diversity. Include a materially different comparator where feasible; otherwise state its absence and narrower claim.

Inspect failures/partial outputs: distinguish capability, task defects, unfair grading, infrastructure and unknown observation. If development tasks are too easy, sample harder source work; do not tune individual cases to defeat a model, hide constraints or artificially shrink resources. Record development selection/exclusions.

Freeze unseen groups before evaluation and publish out-of-band results without reshaping cases after answers. Harder later suites receive new identities; preserve prior results. Difficulty requires actual baseline execution, and challenge calibration stays provisional until validated.

## Acceptance evidence

Link each card gate to evidence or a named gap. Deliver matrix, dossiers, scoring/controls, baseline/repetition plan, observed failure taxonomy and stage decision. Plans are not observations. Apply [benchmarking guidance](../guidance/benchmarking.md) for validity and [benchmark contract](benchmark-contract.md) for records/aggregation.

Separate semantic rubric-development examples from held-out correct alternatives, useful partial work, misleading near misses and incorrect/empty outputs. Save blinded judgments, independent labels, disagreements and adjudication. Author labels leave calibration provisional; exposed examples cease to be held out.

## The destination-collision fix: the decision and what I rejected

Root cause, measured and confirmed by reverting to `1887ee7f`'s version and
re-running my two new adapter tests against it (both FAIL there, both PASS
against my fix -- see "Can-fail / fail-pass readings" below):
`_destination()` computed a path from `item_key` ("skill" or "agents") and
`name` alone, never `kind`. Every home/project surface iterates the SAME
`item_key == "skill"` regardless of whether the ring record being rendered
is a skill or a workflow, so a skill and a workflow sharing one name always
collapsed to one file and the second `plan()` entry silently overwrote the
first at `write()` time.

Fix: `_destination()` now also takes `kind`. For `kind == "workflow"` it
derives `slug = f"{name}-workflow"` and uses that slug ONLY for path
construction, through the SAME "skill" `installed_items` template and the
SAME `AGENTS_ITEM` template already in use -- `render()` still receives the
item's true, unsuffixed `name`, so the generated frontmatter
(`name: super-research`) and body (`tickets.py instantiate super-research
--run <run>`) are unaffected; only where the file lands changes. `stale()`
needed no change: it already globs `root/"skills"/*/SKILL.md`, and the
workflow's adapter still lands under `skills/`, just at a different leaf.

Rejected, and why:
1. Add a `"workflow"` key to `installer/host_adapters/{claude,codex,grok}.json`
   pointing at a distinct template (e.g. a sibling `workflows/{name}/SKILL.md`
   surface). Rejected: those three files are compiled artifacts pinned by
   their own `source_sha256` against `hosts/*.json`; touching them means
   editing the source records, the installer's packaging step, and
   regenerating three hashes -- a schema-level change the Details explicitly
   fenced off ("this is not a licence to redesign the renderer").
2. Render a workflow's adapter under a host-home `workflows/` directory
   instead of `skills/`. Rejected on two independent grounds: (a) none of the
   three hosts scan a `workflows/` directory for invocable items -- only
   `skills/` is a discovery surface any host record names -- so this would
   silently make the workflow un-discoverable by the very hosts clause 3 asks
   it to reach; (b) `stale()`'s glob is fixed to `root/"skills"`, so this
   option would also require touching a second function, which the slug
   approach avoids entirely.
Known residual, reported and left alone: the `-workflow` suffix can still
collide in the narrow, pathological case where a ring separately holds a
skill literally named `"<x>-workflow"` and a workflow literally named
`"<x>"`. Goal clause 5 asks for the ordinary case -- one name, one skill, one
workflow -- which this fix resolves completely; the pathological case would
need a namespacing redesign of the kind Details fenced off, so I named it
rather than building it.

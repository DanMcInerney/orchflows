## Implementation

One shared `orchflows` guidance document covers composing processes and authoring workflows/guidance. Units follow coherent results and consequential dependencies; domain guidance supplies useful signals without mechanically creating a gate per file. The coordinator's planning guidance does not become a task worker's subject guidance or create an extra review unit.

Dynamic gates substantive units with one independent reviewer and one worker for at most one repair pass when needed. It keeps the direct-check exception for small reversible work, core-only guidance selection and selected component contracts. A save/reuse request explicitly composes Build, whose authoring review satisfies that unit without another wrapper.

Build uses the same default for newly authored production workflows. It preserves explicit caller choices and component contracts, leaves other staffing flexible, and retains representative synthetic trials before authoring review. Shared review/check/handoff semantics live in architecture. There are no new per-skill guidance subclasses or workflow execution engine.

## Artifacts and process interpretation

All three generated weekly-plan recipes exposed changing inputs and output locations, avoided hardcoded fixture answers, and described one joined independent review with one conditional fixer. The Build versions extracted planning criteria into local guidance; the Dynamic-save version kept the small contract in the recipe and used core data-analysis/writing guidance. Both layouts are permitted: abstraction is useful when it carries reusable differences, not mandatory for every recipe.

Research → code used six root-dispatched children: two researchers, one research reviewer, two implementers and one code reviewer. The same-domain contract case used five: contract reviewer, contract fixer, two implementers and joined reviewer. The seeded repair case used two: reviewer then fixer. Counts alone do not establish compliance; the audits inspect their source reads, stable candidate identities, actions and dependency ordering. No new unit was invented to obtain another repair.

The direct-check exception had a larger effect than the predictions assumed. The small vendor decision and page each read applicable guidance without creating a review gate. A domain-per-gate rule would misclassify the integrated page; conversely, the contract case shows why two code units can be justified. This pilot supports retaining explicit dependency semantics and measuring the exception, but cannot establish that this boundary policy outperforms alternatives.

Existing named examples retain their contracts. Static inspection of `3d-browser-game` found two playtest checkpoints (core and final); Blender production and scenario QA support those handoffs rather than automatically adding reviews of their own. `design-loop` retains its bounded cycles and independent comparison; `short-video` retains review without an automatic repair loop; `software-factory` retains specialist reviews and candidate passes. The new defaults do not overwrite those explicit processes. These examples were inspected structurally, **not executed** in this pilot.
